# 插件与 reverse-project-management 的协作契约

> 状态：设计规格，尚未实现插件适配层。
> 本文定义 Rea-Multi-agent 的接入方式；通用证据与项目管理规则以实际分析仓库内的 skill 副本和项目配置为准。
> 工具字段、默认值、角色、资源和恢复阶段见[编排契约](orchestration-contract.md)与[工具 Schema](rt-tools.schema.json)；本文件描述 skill 的接入和事实整合。

## 职责分工

| 层 | 负责 | 权威载体 |
|---|---|---|
| reverse-project-management | 目标身份、路线/RUN 结构、封存与来源链、条件和争议复查、项目验收 | 分析仓库的 `docs/agents/reverse-project-management.md`、项目 skill 副本及其规则 |
| Rea-Multi-agent | 岗位与成员、任务交付、并发与资源、操作恢复和尝试隔离；按 skill 规则归档和调用检查 | `re/team/` 的编排记录、宿主名册和任务板 |
| Lead | 选路、审阅原始来源与推理、给出路线判定及影响处置、整合项目记录 | 原有路线/条件/项目记录；INDEX 只作摘要与导航 |
| 工兵 | 执行约定的单轮实验，持续保存计划、运行事实、原始产物、定位和局限 | 本次尝试的独立工作区与提交 |

skill 可独立用于单人项目，也可配合其他编排工具。插件复用 skill 的格式、脚本和证据门槛，不复制一套路线状态或封存算法；技能文本给出工作规则，插件实现确定性的交付、写入和状态检查。平台不会因为加载了 skill 就自动提供事务、锁或验收。

本仓库是插件开发仓库，不因使用本契约就把它初始化为逆向分析项目；下文的项目根指用户选定的实际分析仓库。

## 接入与版本绑定

1. Lead 用 skill 的首次配置规则接入分析仓库。新项目可初始化；已有项目保留目录、历史及项目副本，按差异合并团队规则，不重跑 init。
2. 分析仓库必须有 INDEX、项目配置和可独立运行的 `.agents/skills/reverse-project-management/`。插件 v0 只支持其默认布局与已适配的 schema_version=1 正式记录；其他布局返回可读缺口，不静默另建目录。
3. 项目副本需包含团队协作与工具清单规则，且能执行 `seal`、`impact`、`index`、`check --hashes`、`audit-scope`。没有团队规则的旧副本由 Lead 比较后升级，插件不拿全局副本覆盖它。缺少 Python 或脚本失败是环境阻塞，不是路线证死。
4. rt_roster inspect 的只读接入检查返回兼容性、实际目录及缺口，不落盘。缺服务时固定通过不依赖插件注册的 bin/doctor.mjs 诊断，离线就绪不冒充运行就绪，具体见编排契约。
5. rt_roster bind 按已确认提议首次保存项目根、project/Lead session/team/epoch、adapter contract version=1，以及所用规则和脚本的路径/内容摘要，不立即创建成员。从 INDEX 手写区链接 binding 与 roster。摘要用于判断变化，不冒充独立可信签名。

项目配置的“协作方式”登记此编排契约的项目内副本或稳定版本引用、当前 Lead、工作区与资源规则。项目记录不引用某台机器的全局绝对 skill 路径。使用期间副本变化需重新做兼容性检查并保留旧绑定；未完成尝试继续绑定原规则或显式重派，不能静默换规则。

普通会话恢复重读并核对原绑定，不重建成员。v0 不自动跨 Lead 会话迁移：新会话遇到旧绑定返回 `PROJECT_SESSION_MISMATCH`，由 Lead 按 skill 的恢复规则核实旧执行、保留事实与历史，再显式接管并建立新名册。一个分析项目同一时刻只允许一个 Lead 整合者。

## 记录与写入归属

正式事实全部沿用 skill：`re/targets.json`、`re/routes/`、`re/runs/`、`re/conditions/`、`re/project.json`、`re/env/`、`re/seals/` 和 INDEX。插件仅新增：

| 路径 | 内容 |
|---|---|
| `re/team/binding.json` | 项目/会话绑定、契约版本、规则与脚本摘要 |
| `re/team/roster.json` | 岗位/成员/当前任务的映射与编排状态；历史任务指向 dispatch 记录 |
| `re/team/dispatches/<dispatch-id>.json` | 完整不可变契约、operation ID、任务与路线映射、当前尝试和操作阶段 |
| `re/team/work/<dispatch-id>/<attempt-id>/` | 工兵可写的独立工作区，含计划、原始/派生产物、运行草稿和提交清单 |
| `re/team/receipts/` | 交付、整合、失败恢复的持久回执及检查结果引用 |
| `re/team/audit.jsonl` | 编排事件，引用上述身份和回执 |
| `re/team/capabilities.json` | 工具名或清单 provider 精确绑定、注册表指纹和不可变环境就绪引用 |
| `re/team/resources.json`、`re/team/lock` | 分析资源租用/隔离与项目整合锁 |

工具环境沿用 `re/env/`，新增当前 `tools.json`、从它生成的 `tools.md` 及不可变 `ENV-tools-*.json`。由项目 skill 指导单人执行者或团队 Lead 发布并维护 INDEX 指针，工兵提交发现/验证材料。插件仅消费这些记录，不负责扫描、验证执行或文档生成。RUN 和契约只引用不可变快照及字节哈希，不能引用会刷新的 tools.json。路径、四层状态、原生工具调用与刷新/提醒规则见[工具发现与文档](tool-discovery.md)；现有 project.py probe/check 不实现目录扫描、MD 生成或清单语义检查。

事实层的 route ID、RUN ID 与编排层 task/dispatch/attempt ID 分别保存。一个路线可有多次派发和多个 RUN，一个派发可交回多个 RUN；ID 一经引用不回收。新尝试分配新目录和 RUN ID。未开始即阻塞的任务可以没有 RUN。

Lead 是共享正式记录的唯一写入者；通过插件串行整合，插件持有项目写入锁并原子更新单个文件。工兵只写分配的工作区，读取正式记录，不执行共享项目的 seal/index 或改路线/条件/封存。这里是协作写入约定，仍保留通用文件和 shell 工具，不新增命令门闸。

工作区提交后保持该版本稳定。归档时保存原提交、路径映射及原始字节哈希，将核对过的产物和 RUN 记录放入正式位置；保持实际命令、cwd、时间、来源和采集事件，不能因移动存储而改写执行事实。归档后的正式记录才参与 skill 校验。其他工兵继续写隔离区，避免全项目 seal/check 读到正在改写的正式 RUN。

现有 project.py 不管理 `re/team/`，插件自行校验编排状态；INDEX 通过手写指针导航到编排记录。正式证据必须归档到 skill 支持的位置，不能仅靠编排目录或消息存在就算验收。

## rt_dispatch：把可执行问题交给成员

契约至少绑定：`operation_id`、`post_id`、`route_id`、`target_ids` 及其哈希、`objective`、问题/判据、预算与停止条件、必需锚点、禁止事项、工作目录、资源需求及项目 skill/配置入口。插件生成 `dispatch_id`、`attempt_id` 和 RUN ID 预留；任务创建后补入宿主 task ID/revision 的交付信封，不原地改写原契约。

路线问题、假设、实验和 budget 沿用 skill 的 route 字段，契约引用该路线版本及完整内容摘要，不另建事实层格式。`route.depends_on` 指路线；可选 `depends_on_tasks` 只表达宿主任务的执行排序，两者不得混用。

派发顺序的不变量：

1. 读当前路线与 impact，检查目标身份、有效 validated 依赖、条件版本、争议、恢复待办及已有资源租用。前提未满足时无副作用拒绝；v0 不建等待派发队列。
2. 从岗位模板取得必需能力，合并任务附加需求。缺必需调用通道/入口或已知运行时不适配时不建成员/任务，返回缺口；新成员特定就绪未知时先 bootstrap 无害预检，失败保留已用席位并返回 partial，不开始实验。Lead 可另派 environment 任务，不能删掉模板需求绕过检查。
3. 校验同岗成员是否空闲、席位/activation 额度与资源归属。同一成员最多一个未收口任务；忙碌时返回 `MEMBER_BUSY`。同一目标实例默认独占，独立实例才并行；重派前核查旧副作用及资源实际状态。
4. 持久化操作、契约与尝试身份，再创建/复用成员并创建和指派任务。新成员初始 prompt 只加载角色与项目规则、等待有效任务交付，不能在任务身份建立前执行实验。
5. 新成员与复用成员都收到统一交付信封：task/attempt 身份、契约路径和摘要、项目规则入口。完整契约从持久文件读取，消息不搬运超长正文。消息成功与否写入操作阶段，未交付不能回报派发成功。

成功回执含 operation/dispatch/attempt/task/member/route、任务 revision 与契约引用，任务为 `in_progress`。宿主名册和 task board 是执行状态来源；本地映射提供恢复关联，不能凭旧 JSON 认定成员仍存在。

## 工兵交回与 rt_conclude

工兵在工作区提交清单：身份、RUN 清单和状态、产物/哈希/定位、观察与推断、局限和具体技术问题、前提变化、恢复情况。提交完成后停止改写该版本，并发消息给 Lead。工兵不自行 complete 宿主任务；三个 rt 工具的变更操作均由 Lead 调用，其他身份返回可读拒绝。

`rt_conclude` 输入 task/attempt、提交引用与摘要，以及 Lead 审阅的结论、理由、建议路线变化和影响处置。它按以下顺序收口：

1. 校验当前 owner/revision/attempt、提交摘要、契约与规则版本、目标及前提的当前有效性。失效前提需要 Lead 先给出处置，不能自动采用旧判定。
2. 校验并归档执行记录，依据项目 skill 核对身份/来源/定位。未做实验的阻塞交回只记录问题和检查依据；发生过实验的失败、超时、中断按真实 RUN 状态归档。
3. 调用项目副本 `project.py seal <root> <RUN-id>` 封存尚未封存的终态 RUN；若恢复操作发现已有封存，只校验复用，不覆盖。它以 skill 的封存基线和目标身份做检查，不以本次提交的新哈希替换旧期望值。
4. 按 Lead 的有依据判定更新路线 history/closure、条件/争议和受影响验收。运行 completed 不等于路线 validated；可靠反证才 falsified，缺工具写 blocked，预算用尽写 paused。接收一次交付不要求整条路线终结。
5. 执行 `impact`，处置会阻止当前状态成立的影响，再刷新 `index` 并执行 `check --hashes`。所有脚本失败保留原始诊断与阶段，不继续标任务完成；校验通过不能替代 Lead 对来源和推理的审阅。
6. 持久化预备收口回执后完成宿主任务，核对完成态并保存最终回执再返回 ok。completed 表示本轮交付已处理，不表示分析成功或项目完成；结果使用编排契约的七类 outcome，不把传输阶段 delivered 当成分析结果。下游启动仍须核查路线/条件。

使用原生工具提前完成任务属于协议偏离。插件发现 completed 但无验收回执时标记 `UNREVIEWED_COMPLETION`，不把它计为已验收，不释放事实层依赖；Lead 可走同一收口检查补验，最后核对完成态而不重复 complete。工兵不能直接调用 rt_conclude 自证验收。

路线中的定位和闭合仍以项目 skill 的记录为准：地址绑定模块/目标和基址；文件行号绑定内容身份；Web 结果绑定保留的响应/采集产物；evidence ID 附持久导出。结构与哈希校验不证明结论有效，也不提供对同时改写基线和校验器的独立防篡改保证。

## 恢复、跨路线影响与结束条件

插件为每次变更保留 operation ID、阶段及已有宿主 ID；同一请求重入从已记录阶段继续，不再建成员/任务。相同收口重放返回原回执，内容冲突才拒绝。写事实与完成任务之间失败时，保留已整合事实，恢复后校验再补任务完成；审计写入失败在回执披露，不伪称已写。

宿主变更成功但响应丢失时，先按操作身份关联查询名册/任务；无法唯一确定是否成功，返回 `RECOVERY_REQUIRED`，由 Lead 核查，不能盲目重试消耗席位。本地阶段记录不构成与宿主之间的原子事务。

重派撤销旧 attempt 的提交资格并隔离目录；旧成员和后台任务按 skill 恢复规则核查。迟到提交留作历史，不能覆盖新产物或自动改变路线。隔离目录不能代替对共享外部目标的资源占用控制。

Lead 循环为：读回报与状态 → 处理交付/复查/阻塞 → 派已有独立任务 → 无独立工作时有界 wait → 回读。timebox 从持久的实际开始时间计算，Lead 不运行时不承诺后台超时处置。不为保持忙碌而无限开新路线。

跨路线条件和争议变化按 skill 的 impact、条件版本与人工关联审查处理；影响正在运行的任务时，Lead 通知成员暂停或复核，收口再核对一次。来源路线无需整条完成即可提交其已取得的 RUN，核验并更新条件。

任务板全部完成不等于项目完成。阶段交接和完成由 Lead 依 skill 执行全部历史路线的关联审计与逐目标验收，`check --hashes --complete` 通过后才声明项目完成；预算耗尽则如实交接未完成项目。

## 接缝与验收

插件通过项目管理 adapter 读取正式记录并调用项目副本 CLI。生产 adapter 使用已有脚本；单元测试可替换此接缝，避免在插件里重写封存/来源链校验。CLI 的退出码和 JSON 输出（impact/check/audit-scope）按实际命令处理，seal/index 的文本输出保留作诊断，不发明未提供的参数。

除宿主团队替身测试外，新增不依赖 DSH 的真实 skill 集成验收，使用临时分析项目和非可执行测试数据。正式验收编号见[验收矩阵](acceptance-matrix.md)，涵盖：

- 初始化后项目副本含团队规则和配置指针；旧副本缺规则、非默认布局、缺 Python 时诊断准确，均不覆盖历史。
- 两个工兵并行写独立暂存区，Lead 串行归档；真实 seal/index/check 通过，执行事实、来源与字节哈希保留。
- 正常交付、未开始即阻塞、运行失败、超时、中断和证死分别遵守 skill 的门槛；不因交付已处理就满足成功依赖。
- B 的发现更新 C 后，真实 impact 能报告 A 及下游复查，旧 closure 保留，受影响活动路线与验收得到实际处置。
- 重复请求、阶段失败和响应丢失恢复不重复建岗/建任务；已有 seal 只校验复用，迟到 attempt 不污染新结果。
- 会话绑定不符、共享资源冲突、提前原生 complete、篡改已有封存产物与缺锚点均有明确结果。
- 任务板全完成但验收/审计未满足时，真实 `check --hashes --complete` 仍失败；反向检查通过也不能省略人工证据审阅。

共享 skill 的单元测试不验证 DSH 编排；插件测试不假装 skill 已实现成员管理。完整验收还需真实 DSH 团队会话，但初次设计修订未核对宿主源码；后续已作版本限定的文档/接口核对，仍未通过运行验收。
