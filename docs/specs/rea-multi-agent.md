# Spec：Rea-Multi-agent — 逆向团队的指挥架构

> 状态：待评审（本地文档，不发布到 GitHub Issue）

## Problem Statement

逆向分析是一件长拉锯的事。一次定位、一次反编译、一次动态验证，动辄几十分钟到几小时，而当前只有一个 agent 在干活：它发起一个耗时的分析，就只能停在那里等；等回来再顺着下一条线走。结果是两重浪费——主 agent 的时间被单条路线锁死，那些本来可以同时探的岔路（静态一条、动态一条、协议一条）也一并被串行化。

同时，逆向的价值不在于"跑过一次"，而在于**跑过之后留下了什么**：哪个函数、哪个地址、哪条证据支撑了哪个结论。一个 agent 同时扮演执行者和记录者时，这两件事会互相挤占——执行到一半上下文被压缩，前面辛苦挖出来的锚点就丢了。

用户真正想要的是一个**分工**：主 agent 当指挥，负责拆路线、派任务、核对事实、写文档；一组工兵专门干活，各自守一条路线，干完带着证据回来。工兵不能再去派发，否则编制失控、也没人对事实负责。

## Solution

新增一个 preset「红队指挥」和一个配套 bundle，装在 DSH 上。

选中「红队指挥」后，用户只需要说清目标是什么（一个恶意样本、一个游戏客户端、一个 Web 应用），主 agent 会：

1. 判定目标类别，给出一份**班底提议**——哪几个岗位、每个岗位需要什么工具能力、当前环境缺哪些；
2. 用户确认后，按提议**建岗**（工兵是常驻的具名成员，不是一次性进程）；
3. 对每个岗位**派发一份书面契约**：要什么结论、必须交回哪几类锚点、产物落哪、禁止做什么；
4. 派完之后不等着——去核对刚回来的证据、去写文档、去铺开下一条路线；
5. 工兵把边干边看到的东西不断追加到产物文件里，卡住了就把卡点写成一条具体的技术问题交回，由主 agent 决定换路线、换人还是降级目标；
6. 结论落进项目的路线记录（`re/`），任务板上标完成。

用户全程能看到名册和任务板（会话标题栏的「智能体团队」面板），能点开任意工兵的会话看它的完整过程。

## User Stories

**入口与安装**

1. As a 逆向操作者, I want 在模式选择器里看到「红队指挥」并选中它, so that 我进入团队模式而不影响现有的「红队逆向」单人模式
2. As a 逆向操作者, I want 整个升级是一个可本地 link 安装、可一步移除的 bundle, so that 它坏掉时我不至于重装整个 DSH
3. As a 逆向操作者, I want 现有「红队逆向」preset 一个字节都不被改动, so that 我随时能退回已经调通的工作方式

**班底与建岗**

4. As a 逆向操作者, I want 主 agent 先判定目标类别（binary / game / webapp / mixed）再提议班底, so that 岗位跟着目标走而不是每次现编
5. As a 逆向操作者, I want 班底提议里每个岗位都标注它需要的工具能力族, so that 我在开工前就知道哪个岗位此刻是空岗
6. As a 逆向操作者, I want 缺工具的岗位被显式标记、并被要求"缺什么报什么"而不是自己找替代, so that 我不会收到一堆无法复跑的编造结论
7. As a 逆向操作者, I want 班底起步控制在 4–5 个岗位、并保留 2–3 个空位, so that 中途冒出意外角色（比如临时要拆虚拟化）时有编制可用
8. As a 逆向操作者, I want 混合目标（比如带在线校验的游戏）也能组出班底, so that 不必为了迁就模板把目标硬切成两类
9. As a 逆向操作者, I want 主 agent 在已有同岗成员时复用而不是新建, so that 8 个终身席位不会被无谓烧掉

**派发契约**

10. As a 逆向操作者, I want 每次派发都落成一份结构化契约（路线、目标、必需锚点、产物路径、禁止事项、时限、依赖、能力需求）, so that 事后能审计"到底要求了什么"
11. As a 逆向操作者, I want 契约在派发时就同时写任务板和执行层记录, so that 两个账本不会漂开
12. As a 逆向操作者, I want 派发现场就把"必需交回哪几类锚点"写死, so that 收回来的东西有统一的验收口径
13. As a 逆向操作者, I want 主 agent 派发后必须立刻找到下一件可独立推进的事, so that 它不会盯着第一个工兵发呆
14. As a 逆向操作者, I want 只有真的无路可走时才允许 `wait_agent`, so that 阻塞成为例外而不是常态
15. As a 逆向操作者, I want 工兵被要求边干边把发现追加进产物文件, so that 上下文被压缩之后它还读得回来
16. As a 逆向操作者, I want 工兵卡住时必须交回一条具体技术问题而不是"没搞出来", so that 主 agent 能立刻判断该换路线还是换人
17. As a 逆向操作者, I want 派发失败/超时由主 agent 处置而不是插件自动重试, so that 钱不会烧在同一个错误前提上

**收口与记录**

18. As a 逆向操作者, I want 工兵交回结论时同时交回可复跑锚点（地址、偏移、函数名、证据 ID、文件行号）, so that 我能自己验一遍
19. As a 逆向操作者, I want 结论落进项目的路线记录而不只是任务板, so that 会话结束后证据还在
20. As a 逆向操作者, I want 任务板负责"谁在干什么"，`re/` 负责"证死了没有、凭什么", so that 两个问题各有各的载体
21. As a 逆向操作者, I want 主 agent 对关键结论亲自核对一遍, so that 复核不是听汇报
22. As a 逆向操作者, I want `report.md` 里的每条事实都带锚点, so that 报告可以直接当证据链用
23. As a 逆向操作者, I want 派发与收口留审计记录, so that 出了争议能回溯是谁在什么时候要求了什么

**边界与例外**

24. As a 逆向操作者, I want 一个逆向项目严格对应一个 Lead 会话, so that 班底不会跨项目串味
25. As a 逆向操作者, I want 零碎活（跑个脚本、算个哈希、验一条字符串）走一次性子 agent 而不占编制, so that 常驻岗位的上下文不被垃圾污染
26. As a 逆向操作者, I want 命令门闸彻底消失、连检测工具也不留, so that 我不会再被莫名其妙的拦截打断
27. As a 逆向操作者, I want DSH 自带的工具全部保留（shell、文件、搜索、Web、技能、后台任务、定时、计划模式、workflow）, so that 团队模式不是一个被阉割的壳
28. As a 逆向操作者, I want 工兵调不动派发工具, so that 编制不会指数级炸开
29. As a 逆向操作者, I want 能中断一个跑飞的工兵而不清空它的收件箱, so that 我可以纠正方向再让它继续
30. As a 逆向操作者, I want 能点开工兵的会话读它的完整过程, so that 出问题时不用靠猜
31. As a 逆向操作者, I want Web 应用逆向（侦察、指纹、bundle、接口发现）在范围内, so that 目标带着在线组件时不必换工具
32. As a 逆向操作者, I want Web 攻击动作（重放、注入、越权）暂不实现但预留岗位, so that 以后补工具时不用改架构

## Implementation Decisions

**分发形态**

- 交付物是一个 **bundle**（npm 包 + `dsh.bundle.patch` 指向的 patch 文件），本地 `link:` 安装进 profile 的 `dsh.profile.bundles`。与既有 `@local/dsh-rea-plugin` 同形态，内容不同。
- **零个 `@deepseek-ai/*` 运行时 import**。本地 link 的 bundle 无法解析裸包名，工具参数一律用原始 JSON Schema（对象级 `required: [...]`），不引入 harness 的 schema 库。
- 包内三样：一个 preset 行、两个工具插件（班底 / 派发收口）、一行人设。

**preset**

- 新 preset id `redteam-lead`，显示名「红队指挥」，`order: 6`。既有 `redteam` 不动，模式列表从 5 行变 6 行。
- **工具清单取宿主 `standard` preset 的全量行**（含 shell、文件、搜索、待办、技能、后台任务、定时、Web、计划模式、workflow/delegation、compaction），再追加本包的工具行。这是为了"能力不被阉割"，而不是最小白名单。
- Host 面权限（`danger-full-access` + `approval: never`）**不在本包重复声明**——既有 bundle 已在 profile 层全局设定，重复声明只会制造两份真相。
- 人设由 `@deepseek-ai/dsh-persona` 提供；`dsh-persona` 是 scope-only 的，挂在 preset 里才会盖住全局人格。

**工具面**

三个工具，全部由本包的 plugin 注册：

- `rt_roster` — 输入目标类别与目标描述，输出班底提议：岗位列表、每岗的能力需求族、当前环境的能力缺口、建议人数与空位数。**只提议，不建岗。**
- `rt_dispatch` — 契约化派发的唯一入口。职责依次为：解析/创建路线 → 检查能力需求在当前工具注册表中的可用性 → 查名册决定复用还是新建 → 建任务板条目 → 生成工兵 prompt → 返回回执。对非 Lead 成员直接返回明确的拒绝信息（而不是让底层抛错）。
- `rt_conclude` — 收入任务、结论、锚点集合；把结论与锚点写进路线记录，置任务板条目为完成，追加审计。

**班底模板**

四个内置模板以数据形式存在（`binary` / `game` / `webapp` / `mixed`）。每个模板是一个岗位数组，每个岗位至少包含：标识、显示名、关注面、能力需求族、默认验收锚点类型、该岗位的禁止事项清单。

- 模板**可扩编**：Lead 可以在提议之上增删岗位，但新增岗位必须给出能力需求族，否则派发时无法检查空岗。
- `mixed` 不是独立技能集，而是取交集并保留空位。

**派发契约字段**

必填：`route`、`objective`、`target`、`deliverable_path`、`evidence_required`、`prohibited`。
可选：`timebox_ms`、`context`（fresh / fork）、`depends_on`、`capability_needs`（缺省从模板岗位继承）。

契约生成工兵 prompt 时，必须把"边干边落盘""卡住交具体问题""缺工具就报缺"三条行为规矩写进去——这三条是任务级约定，不依赖人设。

**双账本**

- 任务板 = 执行层，存在 Lead 会话日志里，随会话生命周期结束。
- `re/` = 事实层，随项目存活，包含路线、证据、证死记录、封存。
- `rt_dispatch` 一次写两处；`rt_conclude` 把任务板完成态同步到路线记录。不靠人设自觉维持一致性，写在工具实现里。

**编制约束**

- 工兵是常驻岗位，席位终身不回收；因此派发**先查名册**，同岗空闲成员直接投喂新任务，不新建。
- 裸 `subagent` 只用于零碎活，不占编制；它自身有并发上限且超限抛错，不做队列，调用方需自行收敛。
- 一个项目 = 一个 Lead 会话。项目完结即存档，新项目新开会话以取得干净席位。

**边界**

- 删除命令门闸：不注册任何 `tools/pre-execute` 拦截，不提供命令扫描工具，不写拦截审计。
- 审计只记录派发与收口（谁在何时要求了什么、交回了什么），不复审命令。
- Web 攻击动作不实现；对应岗位存在但能力声明为空，派发时会被标为空岗。

**项目记录**

沿用既有的逆向项目管理约定：`INDEX.md` 为总入口，`re/` 下按路线组织，证据以封存形式累积。`rt_dispatch` 创建或更新路线，`rt_conclude` 写入结论与证据引用。

## Testing Decisions

**两层，两个接缝。**

**第一层：工具处理器（自动，`node --test`）。** 所有决策逻辑通过三个工具处理器暴露，测试直接调它们，**只替换两样东西**：团队服务（名册、任务板、spawn）与项目文件系统。这一层不启动真实 agent、不装载 preset，跑得快，任何改动后都能全量重跑。

这一层的团队服务用**契约级替身**，不是随手 mock 几个方法：它必须实现已核实的对外契约——成员角色 `lead|teammate`、`spawnTeammate` 只接受 lead、任务板状态机与 `blockedBy` 依赖校验、`expected_revision` CAS、成员名规则与席位上限。替身与真服务的偏差由第二层兜住。

好测试的标准：给定一个项目状态和一个派发请求，断言**可观察的结果**——路由是否被创建/复用、任务板条目是否建立、是否有成员被创建、返回的能力缺口清单是什么。不断言内部函数名、不断言日志文案、不断言调用顺序。

**会被测试的行为**

- 班底提议：四个模板各自产出的岗位集合非空、每岗能力需求非空；`mixed` 产出交集且保留空位；缺口清单在注入"某工具族不可用"时正确列出。
- 派发：同岗已有空闲成员时不新建；无成员时新建一次；契约字段缺失时拒绝；能力缺口被带入 prompt；非 Lead 调用被拒绝且返回可读原因。
- 收口：结论与锚点写进路线记录；任务板条目转为完成；重复收口同一任务被拒绝。
- 双账本：一次派发后，任务板与路线两侧都能观察到同一条路线的痕迹。
- 路由编号：同一项目并发派发不会产生重复路线号。

**先例**

沿用既有插件包的测试风格：`node --test` + 显式文件路径，用临时目录搭项目状态，纯函数优先、I/O 集中在边界。

**第二层：真服务验收（半自动，一次性会话）。**

这一层必须跑真实的 `ctx.agentTeams`。它不能塞进 `node --test`：宿主包只存在于打包的 `app.asar` 里，机器上没有可 import 的副本（`app.asar.unpacked` 下没有 `@deepseek-ai`），裸 `node` 也无法从 asar 里 require。所以第二层在**一个专门的一次性 DSH 会话**里执行——真实服务、真实 spawn、真实会话日志。

步骤与通过标准：

1. 建一个临时逆向项目目录，装好本 bundle，用「红队指挥」开一个会话；
2. 调 `rt_roster` → 通过标准：岗位数 ≥ 4、每岗能力需求非空、缺口清单与当前工具注册表一致；
3. 调 `rt_dispatch` 派一个岗 → 通过标准：`list_agents` 出现该成员且 `role=teammate`、`team_task_list` 出现该任务且 `status=pending`、`re/` 下出现对应路线、回执里的路线号与任务号能对上；
4. 对同一岗再调一次 `rt_dispatch` → 通过标准：**没有**新成员出现，任务板多一条任务，成员仍是同一个（席位没被烧）；
5. 从工兵侧尝试调 `rt_dispatch` → 通过标准：被拒绝并返回可读原因，且没有产生任何成员或任务；
6. 调 `rt_conclude` → 通过标准：任务转 `completed`、路线记录里出现结论与锚点、审计文件多一条记录;
7. `interrupt_agent` 中断该工兵 → 通过标准：返回 `previousStatus=running`、成员仍在名册、可被 `send_message` 唤醒继续。

会话是一次性的，验收完即丢——因为**席位终身不回收**，这个会话里建出来的成员会永久占位。验收记录（会话 id、`list_agents` 与 `team_task_list` 的原始输出、路线文件与审计文件的 SHA-256）提交到 `docs/verify/` 下，任何人可以照步骤重跑。

**不自动化**

preset 是否挂载成功不进自动化——模式选择器里出现「红队指挥」、且该 preset 的工具清单包含宿主全部工具，这两条由第二层的步骤 1 顺带确认。

## Out of Scope

- 不改动既有 `redteam` preset 与既有 `@local/dsh-rea-plugin` 包的源码或配置
- 不做命令门闸、命令审计、危险命令检测工具
- 不做 Web 攻击能力（重放、注入、越权、凭据管理、扫描器）
- 不做嵌套团队（平台按成员角色硬拦，无法绕过）
- 不做队友的模型档位选择（平台不提供该参数）
- 不做自定义 UI（复用团队插件自带的名册与任务板面板）
- 不做派发自动重试
- 不做跨项目的班底迁移
- 不发布 GitHub Issue；本 spec 即为唯一书面依据

## Further Notes

**三条被事实定死的约束**（来自对宿主实现的核对，不是偏好）

1. 团队成员的席位终身不回收，只减不增——所以"一个项目 = 一个会话"不是洁癖，是唯一可行的编制方案。
2. 任务板存在 Lead 的会话日志里，任务完成**不会**唤醒 Lead，只有 `wait_agent` 的等待者会被满足——所以"派完自动收通知"这个模式不成立，Lead 必须有可做的下一步。
3. 一个 agent 的团队工具是按"成员身份"注册的，不是按 preset 注册的——所以 Lead 身份与选哪个 preset 无关；这也意味着同一个 profile 下任何 preset 的根 agent 天然都是 Lead。

**一条被移除的设计**

命令门闸（拦截格式化磁盘、清空卷影副本、破坏引导配置等操作）已确定整体删除，连检测工具也不保留。判断依据是这类操作与逆向无关，且当前模型不会主动执行；代价是失去了对不可撤销操作的唯一技术兜底，这一点在项目文档中如实记录。

**关于"能力不被阉割"的解释**

新 preset 声明宿主 `standard` 的全量工具行，而不是像既有红队 preset 那样裁剪白名单。理由是团队模式下指挥要做的事跨度极大——读文件、跑命令、开后台任务、跑 workflow、查 Web、写计划——任何一项缺失都会把活推回给用户。
