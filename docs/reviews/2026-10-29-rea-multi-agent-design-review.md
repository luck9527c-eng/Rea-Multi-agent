## 判断

方向清楚，三工具也可以继续保留，但规格目前更充分地描述了“宿主允许什么”，尚未定义完整的“插件如何确保一次派发可靠地走到验收”。建议先补齐下列 P1，再进入实现。P1 指会破坏明确需求或导致核心流程不可用；P2 指需明确的行为和验收边界。

## P1-1：工兵先 complete 与收口校验互相冲突

位置：spec 第 166–174、187、205、249 行。

规格要求工兵完工后自行 `complete`；另一方面，`rt_conclude` 要把任务从 `in_progress` 置为完成，第一层测试还明确拒绝非进行中任务。这意味着工兵遵守要求后，正常收口反而没有合法入口。

更严重的是，按本文对依赖的定义，工兵自行完成任务就会释放依赖；尚未通过锚点与哈希检查的结果可以驱动下游。之后收口拒绝，也不能撤回已经开始的工作。

建议选定唯一的业务完成语义。最小方案是工兵只提交结果，Lead 调用 `rt_conclude` 验收并完成任务；工兵不直接调用原生完成工具。若必须由工兵完成执行，则需另设持久的验收状态，并明确下游依赖验收状态，而非仅看任务板完成态。由于原生工具仍可见，需说明绕过插件完成时如何识别和处理。

补一张结果状态表，至少区分已验收结论、未发现、阻塞、执行失败、取消；不要把“没有继续执行”和“结论得到证实”压成同一种完成。每种结果是否满足依赖应写清。

验收：工兵先提交、校验失败时下游不得启动；校验成功后才能释放相应依赖；正常提交能够收口。

## P1-2：复用成员的派发协议缺失，首派也存在启动窗口

位置：spec 第 51、154–170、247、261–263 行。

完整契约只定义为写入 `spawn_teammate.prompt`，但已有成员复用时不会再 spawn。规格未规定如何把新契约、任务 ID、修订号交给该成员，也未规定收到消息是否代表已开始该任务。

同岗忙碌时应拒绝、等待，还是允许同一成员挂多个任务，也没有决定。第一层只保证“空闲时复用”，真服务步骤 4 却无条件要求再次派发不增成员，测试前提不一致。

首派也需交代：若 spawn 的初始 prompt 会立即开始工作，而任务尚未创建或指派，成员能否执行、向哪个 task 提交？这不是要求核对宿主，而是无论采用什么宿主顺序都需要定义的交付不变量。

建议把契约先持久化到任务专属文件，派发统一传递契约引用、摘要哈希、task ID、attempt ID。规定新建与复用各自的启动顺序，成员只能在收到有效任务身份后工作。复用用消息交付时，明确长度超限处理，不能套用 spawn 的无限长假设。v0 可直接规定每个成员最多一个未结束任务，忙碌时返回可读冲突。

验收：空闲复用、忙碌复用、长契约，以及成员启动早于指派完成，均有确定结果。

## P1-3：双账本一致性只有承诺，没有部分失败与重入规则

位置：spec 第 170、183–187、219、249 行。

一次派发涉及路线文件、岗位映射、成员创建、任务创建、指派和消息交付；一次收口涉及结果写入、索引更新、任务完成及审计。任意一步失败或响应丢失，都可能留下部分成功。成员创建还会消耗不可回收席位，无法简单回滚。

例如任务已经创建、调用回执丢失，再调一次是继续旧操作还是创建新任务？路线已写、complete 失败，是已收口还是未收口？“一致性写在实现里”不能回答这些问题。

建议请求带稳定 `operation_id`，持久化操作阶段和已取得的宿主 ID；重入先恢复原操作。规定文件原子更新、同项目写入串行化、修订冲突处理，以及部分成功时的结构化回执。相同收口请求重放应返回先前结果，内容不同的重放才报冲突，不能把所有重复调用一律拒绝。审计 best-effort 可以保留，但回执应指出审计是否落盘。

验收：在每个可产生副作用的阶段注入失败及回执丢失，重试后不重复建成员、不重复建任务，最终状态可解释且可恢复。

## P1-4：重派没有隔离旧执行，旧结果可能覆盖新结果

位置：spec 第 154–155、178–181、217 行。

卡活的首个动作被规定为先解绑，但解绑 owner 并不等于旧成员或它启动的后台任务已经停止。新成员开始写同一 `deliverable_path` 后，旧成员仍可能继续写入或迟到提交。只在收口时检查 owner/revision，不能阻止共享产物文件被覆盖；相同成员重派时还需要区分不同尝试。

建议每次执行具有递增 attempt/generation，使用独立的尝试目录。重派先撤销旧尝试的提交资格，再中断或处置旧执行；收口只接受当前 attempt 的结果。明确中断 agent 是否包含它发起的后台任务，不包含时由谁清理。旧文件可保留为历史证据，不自动并入当前结论。

验收：A 被重派给 B 后迟到提交，或 A 的旧后台任务继续写入，均不能改变 B 的产物与验收状态。

## P1-5：服务缺失时的诊断入口不可达

位置：spec 第 42、96–98 行。

这里直接写明：插件强依赖 `agentTeams`，缺失时工具插件静默 pending；随后又要求“首次调用返回诊断”。按同一段的前提，工具未注册就没有首次调用可处理。这是规格内部矛盾，不需要核对源码才能发现。

建议把诊断放在不依赖团队服务的入口：例如独立安装自检，或在宿主支持时采用可选依赖并始终注册诊断入口。具体机制可以实现时选，但必须保证缺服务时用户仍有可达的检查路径。

验收：在未启用团队 profile 的环境中，从真实可见的入口得到修复指引；不能只测试已挂载处理器返回错误。

## P1-6：能力检查尚不能决定能否派发

位置：spec 第 47–48、141–155、226、245–247 行。

目前只有能力族名字及匹配函数，没有工具名到能力族的映射规则。即使名字匹配，也只能证明工具已注册，不能证明所需后端连接可用。更关键的是 `capability_needs` 可选，缺能力的测试只要求写进 prompt，没有规定是否阻止 spawn 与任务指派；因此调用方可以省略需求来绕过空岗规则。

还存在直接冲突：新增岗位必须声明能力需求、测试要求每岗需求非空，但 Web 攻击预留岗被定义为能力声明为空。若按通常的集合匹配规则，空需求会判为已满足，而不是空岗。

建议工具内部从岗位模板取得需求，再合并任务附加需求；调用者不能删掉模板的必需项。为各族写匹配表及版本，区分必需、可选、显式禁用/预留；预留岗不能靠空数组表示。v0 可以只保证“工具存在性检查”，但运行时不可用应返回具体阻塞结果。明确必需能力缺失时无派发副作用。

验收：省略需求、未知能力族、预留岗、工具已注册但后端不可用，均有明确结果。

## P1-7：封存校验缺少先于执行的基准

位置：spec 第 69、201–213、230、250–251 行。

重算哈希需要与一个先前确定的期望值比较，但规格没有定义谁在何时建立封存清单、清单记录什么、收口读取哪个版本。若样本和同目录清单同时被覆盖，仅对当前文件与当前清单比较仍可能一致；若期望值直接来自本次提交，也只是自洽检查。

建议在派发前记录基准版本及其摘要，把引用绑定到本次契约；收口对照该版本，不把新提交值作为旧基准。新增证据可产生新版本，不能原地替换旧基准。明确缺失、删除、零文件以及读取失败的行为。

不必因此添加命令拦截，但需精确表述保证：这能发现相对于既定基准的变化；当所有文件和基准均可被同一执行方改写时，它不提供独立的防篡改保证。

验收：修改样本、修改清单、同时修改两者、删除封存项，各自都按绑定的旧基准得到确定结果。

## P1-8：成员并行没有共享分析资源的占用规则

位置：spec 第 21、31、141、154–155、189–199 行。

规格约束了 agent 名额，但没有约束它们共用的调试目标、分析数据库、浏览器页面、工作目录或后台服务。同样具备某种工具的两个成员，可能连接同一个有状态实例：一个切换样本、断点或页面，另一个得到的定位证据就失去上下文。席位足够不能保证这些操作可以并行。

建议至少声明 `resource_key`、共享/独占模式，以及“独立实例或独占串行”的规则。可以由插件记录租用，也可以在 v0 明确只支持外部已隔离实例，但不能默认为所有岗位可并行共用。说明资源释放与中断后的残留处置，并在契约中标明绑定的目标实例。

验收：两个任务申请同一独占目标时不能同时开始；独立实例可以并行；中断后不会把仍在使用的资源直接发给下一成员。

## P2-1：mixed 的交集规则没有覆盖混合目标的需求

位置：spec 第 46、50、141–144、245、260 行。

`mixed = 取交集` 没说明交集对象是岗位、能力还是目标子集。若是岗位交集，游戏 + Web 只留下共同岗，恰好删除两个领域各自的专岗。四种模板也没有实际岗位清单，无法判断“岗位跟目标走”是否成立；真服务统一要求至少四岗，与席位不足时压缩提议的要求也不一致。

建议写出最小岗位表。混合目标通常应先合并所需岗位、按职责去重，再按预算裁剪，同时报告被裁掉的覆盖面；如果坚持交集，给出为何仍覆盖两个目标的例子。验收按输入目标和剩余额度判断，不固定要求所有情况 ≥4 岗。

## P2-2：锚点闭集没有覆盖已声明的全部交付物

位置：spec 第 16、66、81、207–213 行。

需求包括函数名、文件行号与 Web 侦察，闭集却只列地址、文件偏移与 evidence ID。源码函数、bundle 行号、请求响应和运行时观察如何表达？什么情况下可以交“没有发现”或“因缺工具阻塞”，而不被缺锚点一律拒收？

建议定义锚点的带类型结构和结果类型对应的证据要求。源码位置应绑定内容版本；Web 结果应引用保存的响应或采集产物，而不是只给会变化的 URL。函数名应绑定目标与定位上下文。哈希与结构校验只能证明引用完整，结论是否由证据支持仍需明确由谁核对。

验收至少各有一例：二进制、源码、Web、证死/未发现、阻塞结果。

## P2-3：长期项目缺少会话绑定与恢复边界

位置：spec 第 74、185–187、217、230、267 行。

规格以长拉锯为问题背景，却只规定“一个项目严格对应一个 Lead 会话”。持久化 roster 未包含 project/team/session 身份，旧任务 ID 和成员名只在旧会话中有意义。恢复已有会话、旧会话不可用后用新会话打开同一目录、两个 Lead 同时打开同一项目，应分别怎么办尚未定义。

建议清楚区分同会话恢复与新会话接管。至少持久化项目、team/session、schema version；读取时验证绑定并防止两个 Lead 同时写入。如果 v0 不支持新会话接管，显式报错并保留旧事实记录，不把旧 roster 当成新团队名册。任务引用应带所属会话。

验收：重新加载同一会话不重复建岗；新会话遇到旧 roster 不错误复用；第二个 Lead 的写入被阻止或进入明确的只读模式。

## P2-4：Lead 的调度循环与依赖暂存仍由模型临场决定

位置：spec 第 58–62、174、180、287 行。

宿主不推送完成事件，而 spec 只要求 Lead“找下一件事”，没有规定何时回读、何时等待、何时停止派发。Lead 可能持续拓展路线而迟迟不验收；依赖未完成的 dispatch 又允许“等后再派”或“先建 pending”两种不同结果，尚未形成同一个工具契约。

建议写一个最小调度循环：读回报与状态 → 处理待验收及阻塞 → 派发已有独立任务 → 无独立工作时有界等待 → 回读。时间盒以持久化的开始时间计算，不承诺 Lead 不运行时仍能触发超时。明确所有任务结束后的项目退出条件，避免为保持忙碌而无限开路线。

`rt_dispatch` 对未满足依赖选择一种结果：无副作用拒绝，或持久化待派计划并明确之后由谁激活。若采用后者，回执与验收应允许“尚未开始”，不能统一断言 `in_progress`。

## P2-5：工具契约与验收还缺几项可判定输入

位置：spec 第 90、139–170、217–219、259–265 行。

建议补一页三工具的输入输出表，而不增加工具数：调用角色、岗位 ID、任务/尝试 ID、项目根、参数默认值、成功/阻塞/部分成功回执、稳定错误码。当前派发字段没有岗位 ID，收口也没有完整 schema；单个 roster `task_id` 如何容纳历史任务尚不明确。

所有项目路径应明确相对根、允许写入范围、路径规范化及文件/目录类型，避免不同调用各自解释 `deliverable_path`。这是插件自身文件写入的正确性约束，不是命令门闸。

真服务验收还需调整两点：

- 工具名集合无法区分同名工具来自哪个插件；应检查解析后的工具参数/描述或一次行为调用。
- 裸子代理按 spec 第 288 行拿不到团队工具，因此不能用它验证 teammate 的真实团队工具行为。角色拒绝用真实 teammate 验证，裸子代理另测；不要把“工具不存在”和“depth 拒绝”混为一项成功断言。

## 建议修订顺序

1. 先决定“结果提交 → 验收 → 依赖释放”的唯一语义及各种终态。
2. 定义新建/复用派发协议、operation/attempt 身份和部分失败恢复。
3. 固定能力缺口策略、证据基准和共享资源规则。
4. 再补模板表、会话恢复范围与调度循环，按这些规则改验收。

以上均可保留当前三工具与宿主团队面板。关键是把状态、重入和资源协调收进工具的 interface，让 Lead 负责判断分析方向，而不是临场维护隐含的一致性协议。
