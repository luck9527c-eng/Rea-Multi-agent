## 9. 本轮发现（缺陷、观察、已验证的实现事实）

### 9.1 缺陷（已修，含红→绿用例）

**`finding` 落在已是 `active` 的路线上时，路线证据永远不落盘。**

- 现场：`r2-s6b-route-R-001.json` —— `status: "active"`、`evidence: []`；RUN 已 seal、回执已写、
  任务已 `completed`，但路线里没有任何证据。`r2-s6b-diff.json` 里也没有 `re/routes/R-001.json`。
- 根因：`buildRouteUpdate()` 用 `from === nextStatus` 判 `changed`（`src/conclude.ts:908-910`，修复前的行号），
  而调用方只在 `changed === true` 时写文件（`src/conclude.ts:1418`）。状态没变 ⇒ 内存里合并好的
  `evidence` 被丢弃。
- 修法：`changed` 改为"**受管字段**（`status`/`evidence`/`state_reason`/`resume_when`/`closure`）与磁盘上的路线
  不同"，`historyAppended` 仍严格只在状态迁移时为真（无迁移不追加 history）。见 `MANAGED_ROUTE_FIELDS`。
- 用例（`test/conclude.test.mjs`）：
  1. 「finding 落在已是 active 的路线上 → 已落盘路线补上该 RUN，history 不增长」（**先红**：`actual: []`，
     `expected: ['RUN-1']`）；
  2. 「真实状态迁移 → 证据与 history 都落盘」（回归守卫）；
  3. 「无变化的收口不重写路线文件（不无条件打戳）」（防"恒为 true"的过度修复）。

### 9.2 覆盖缺口（`not-run`，只记录不实现）

被篡改的**已封存**产物，若**不在**本次提交的 `artifacts` 列表里：本包的 baseline 比对**抓不到**它
（`compareBaseline()` 只哈希 `baseline.targets` / `baseline.artifacts`，`preexisting_seals` 只比 seal 文件
自身的 path+sha256；而真实派发从不给 `artifacts` 填值），唯一检测点是最后的 `check --hashes`，那时路线已回写。
本轮 6c 是因为产物**在**提交列表里才提前到 `SUBMISSION_INVALID`。**没有用例覆盖这条路径**，
按 `not-run` 缺口登记在 [DECISIONS D37](../../impl/DECISIONS.md)。

### 9.3 预期行为（不是缺陷）

`checks/check-hashes.json` 里 `audit_pending: true` 是**预期**：审计在检查之后写（顺序是
checks → 路线 → impact → index → check → 完成任务 → 回执 → 审计），skill 级 stage audit 属交接待办。
记在 [DECISIONS D38](../../impl/DECISIONS.md)。
