# T22：门禁不稳 —— `lock.test.mjs` 在并发负载下约 25% 概率红

状态：**已完成**（2026-10-30）。**而且根因不是测试问题，是产品缺陷** —— 下面第 3 行那句"不是产品缺陷，是测试问题"是当时的误判，已被本节推翻。

## 定论：锁发布的可见性窗口（真 bug）

`acquire()` 走 `tryCreateExclusive()` = `writeFile(path, bytes, { flag: 'wx' })`：
**`O_EXCL` 先把文件名建出来，再写正文**。两个 acquirer 撞在一起时，败者会拿到 `EEXIST`，
然后按代码去 `readLock()` 读持有者 —— 如果此刻正文还没落，读到的是**零长度**文件，
`JSON.parse` 失败 → 抛 `RECOVERY_REQUIRED`。

于是：**一次完全正常的并发冲突，被报成了「锁损坏」**。而 L2 用例的重试循环只认 `PROJECT_BUSY`，
`RECOVERY_REQUIRED` 直接冒泡 → 用例红。这就是那个"约 1/3 概率、快速失败"的现象。

证据链：
- 观察到的原始报错是 `RECOVERY_REQUIRED … re/team/lock`（不是 `holders === 1` 断言失败）——见 T27 执行报告。
- 用例里 `holders` 在 `acquire()` **成功之后**才自增，中间没有 await 点，所以它不可能真变成 2；
  `acquire` 也用 `O_EXCL`，不存在"两把都拿到"。**所以失败点必然在败者的读回路径上。**
- `src/lock.ts:260`（原）`if (!created) { const holder = await readLock(root) // 损坏时抛出 RECOVERY_REQUIRED }`。

## 修法

`src/lock.ts` 的 `acquire()` 拒绝分支改为区分两种"读不出来"：

| 情形 | 判定 | 理由 |
|---|---|---|
| 锁文件**零长度** | `PROJECT_BUSY`，`details.holder=null`、`holder_unreadable` 说明"正被另一个写者发布" | 正是发布窗口；这是普通并发冲突，调用方重试即可 |
| 锁文件**非空但解析不了** | 仍抛 `RECOVERY_REQUIRED` | 真损坏，**绝不当成没锁**（老规矩不动，既有用例仍绿） |

配套回归用例：`test/l2/lock.test.mjs`「锁文件存在但内容不可读：报 PROJECT_BUSY 并标出读不出来，不报成锁损坏（T22）」
—— 直接造一个零长度锁文件，**确定性复现**那个窗口。

## 遗留（未做，低优先）

`release()` 的 `readLock()`（`src/lock.ts:294`）在理论上也可能读到零长度内容。实践上它只在**自己持锁期间**被调用，
那时正文早已落盘；但如果将来有别的读者（doctor / 旁路巡检）在窗口内读，同样会看到假损坏。
彻底的解法是把 `tryCreateExclusive` 改成「临时文件写满 → 硬链接到目标名」的原子发布，
但那需要给 `AtomicIo` 接口加 `link`（现在只有 `appendFile/mkdir/readFile/rename/rm/writeFile`），另立票。

## 已排除

1. **不是临时目录撞车**：`test/helpers/tmp.mjs:26` 用 `mkdtemp(join(tmpdir(), prefix))`，每个用例独立目录。
2. **不是锁的 fail-open**：`src/lock.ts:7` 写明「过期时间不作为自动解锁理由：`isStale()` 只报告，`acquire()` 永远不会抢锁」；`lock.ts` 里没有任何 `timeout`/降级放行路径。所以负载不会把"拿不到锁"变成"没锁也写"。

## 剩下的两个假设（待查）

1. **测试自身的并发编排**：该用例用两个 async "整合任务"并发跑「拿锁 → 真实 `project.py seal` → 释放」，并在窗口内断言 `holders === 1`。
   计数器的自增与取锁/放锁不是原子的 —— 若断言点恰好落在"第一个已释放、第二个刚取到"的边界，可能读到瞬时值。
2. **同文件三条用例共用一个项目根**：本文件第 2 条是「锁持有者崩溃：只报告 stale」，若它留下的 stale 锁在负载下清得慢，第 3 条会**快速失败**（与观测到的 184ms 吻合）。

两者都指向**测试隔离**，与产品行为无关；但第 2 条若成立，说明同文件内用例顺序耦合，值得顺手拆开。
